# Cloud storage libraries (issue #247)

Owner decision 2026-10-19: people who already keep music in their own cloud storage can stream it in Stash and download it for offline, in the app and the web player. Both stream and download. Start with OneDrive in the app; then Dropbox; Google Drive only if the folder-picker test passes (below). Web player follows with the same providers.

## Ground rules

- The user's own files only. The audio goes straight from their cloud to their phone or browser. No Stash server ever fetches, proxies or stores audio or the user's cloud tokens (see the legal-risk notes: a dev-run machine moving audio is what got Echo Music taken down).
- No "save into your cloud" via a server. A later, optional client-side "upload my downloads to my cloud" is fine; not in this slice.
- Cloud songs are never sent to the lossless relays, never matched or swapped for an online version, never scrobbled differently from local files.
- A build without a client id (plain checkout, CI) has the feature hidden, like the Last.fm keys.

## What other players taught us (research 2026-10-19)

- Siku (OneDrive, open source): placeholder `onedrive://<id>` URIs resolved to `@microsoft.graph.downloadUrl` when ExoPlayer opens them, cached ~5 min because every seek reopens the source; tags from a 256 KB range read (93% of a 765-file FLAC library), a second exact range for a big embedded cover; `/delta` with a saved token; ~5 requests/s throttle with playback first; honour 429 Retry-After.
- Tempus: cache key = provider + file id, never the URL (tokens and links change). Separate stream cache (evicting) and download store (never evicted).
- CloudAmp: Drive sends no Content-Length on some answers; set the length from the file's metadata size or seeking breaks (Android Auto too).
- Symfonium: first scans of big libraries are slow and data-heavy; make the scan resumable and say Wi-Fi is best.

## Provider facts that shape the design

- OneDrive (Graph): `Files.Read` + `offline_access`, no admin consent, personal and work accounts, free app registration. `/content` 302s; use `@microsoft.graph.downloadUrl` (pre-authenticated, Range → 206, may expire within minutes). `delta` per folder; a 410 means rescan. Throttling: honour Retry-After.
- Dropbox: PKCE + `token_access_type=offline`; `get_temporary_link` (4 h); `list_folder` + cursor. 500-user cap until production approval (review opens at 50 linked users, 2 weeks to pass).
- Google Drive: `drive.readonly` is a restricted scope (yearly CASA audit, 100-user cap until verified). `drive.file` + Picker with folder selection is non-sensitive, but it is undocumented whether a picked folder grants its children and files added later. TEST BEFORE BUILDING: pick a folder, then `files.list q="'<folderId>' in parents"`, then add a file to the folder in Drive and list again. 1 TB/day download allowance per project, shared by every user.

## App design (OneDrive first)

1. **Sign-in:** AppAuth (already in libs) with PKCE against `https://login.microsoftonline.com/common/oauth2/v2.0/{authorize,token}`, scopes `Files.Read offline_access User.Read`, redirect `${applicationId}://oauth/onedrive` (so debug and release both work). Client id from `local.properties` `ONEDRIVE_CLIENT_ID` → `BuildConfig.ONEDRIVE_CLIENT_ID`; empty = hidden. Tokens in the Tink-encrypted token store, single-flight refresh. Read-only scope: Stash never writes to the drive in this slice.
2. **Folders:** after sign-in the user browses their drive and picks one or more music folders (default suggestion: a folder named Music). Stored per account.
3. **Scan (WorkManager, resumable):** `delta` on each picked folder; audio by extension and mime (flac, mp3, m4a/alac/aac, opus, ogg, wav); tags from a ranged read of the head (ID3v2, FLAC metadata blocks incl. PICTURE, MP4 `moov` may be at the end: allow a tail read), cover from embedded art or a sibling cover/folder/front image; fallback title from the filename and artist/album from the folder path. Remember item id, eTag/cTag, size, path. Next scans use the saved delta link; changed items re-read, deleted items removed. Throttle ~5 req/s, Retry-After on 429/503, playback requests jump the queue. Network rule follows the existing download setting (Wi-Fi by default).
4. **Library:** cloud songs are real library tracks (like, add to playlist, queue, download, share), with a "Cloud" filter/badge and their account named. Not candidates for online matching, lossless lookups or relays.
5. **Playback:** `stash-cloud://onedrive/<accountId>/<itemId>` handled in `StashMediaSourceFactory` by a resolving `DataSource`: fetch the item's `@microsoft.graph.downloadUrl` (cache ~5 min per item), open with Range, set length from the item size; on 401/403/404/410 refresh the token and/or link and retry once at the same position. Stream cache keyed `onedrive:<itemId>:<cTag>`.
6. **Download:** through the existing download pipeline, from the resolved link; the file lands where other downloads land and the track becomes downloaded (plays from the file after that).
7. **Settings:** Accounts › OneDrive (connect, disconnect = forget tokens and remove its cloud tracks unless downloaded, after a confirm); Library & Storage › Cloud folders (add/remove folders, Rescan now, last scan status).
8. **Disclosure:** PRIVACY.md gets a OneDrive entry (Graph + its download host, what is sent, read-only), README one line.

## Google Drive: pick your songs (owner decision 2026-10-20)

Tested 2026-10-20 on a real account with the web Picker under `drive.file`: picking a FOLDER grants none of its children (`files.list` returned 0); picking FILES (multiselect) grants exactly those, and `GET /drive/v3/files/{id}?alt=media` with `Authorization: Bearer` + `Range` answers 206. `drive.readonly` is restricted (yearly paid CASA audit), so Google Drive is a "pick your songs" provider, not a folder-sync one.

1. **Sign-in = the picker.** Android Picker through Google Identity Services, `com.google.android.gms:play-services-auth:22.0.0` (first version with `PICKER_ALLOW_FOLDER_SELECTION` and `setPrompt`; checked in the AARs): `Identity.getAuthorizationClient(context).authorize(AuthorizationRequest.builder().setRequestedScopes([drive.file]).setOptOutIncludingGrantedScopes(true).addResourceParameter(PICKER_OAUTH_TRIGGER, "true").addResourceParameter(PICKER_ALLOW_MULTIPLE, "true").addResourceParameter(PICKER_MIMETYPES, <audio types + folder>).setPrompt(CONSENT [| SELECT_ACCOUNT]).setAccount(<known account>))`; the result's `pendingIntent` is launched from Settings; `getAuthorizationResultFromIntent` gives the access token and `tokenResponseParams["picked_file_ids"]` (comma list). Folder selection stays off (a picked folder grants nothing); folders stay visible for navigation. The Android picker has no "start in folder" option, so "Add more" can't open in the last pick's folder. Identity: Drive `about` (`permissionId` = account id). No web client id, no server auth code: Google matches the Android OAuth client by package + signing SHA-1. Feature flag `GOOGLE_DRIVE_ENABLED=true` in local.properties.
2. **Tokens.** No refresh token on Android. The token manager's refresh slot holds the account email; "refresh" = `clearToken(stale)` then a silent `authorize()` for that account (no prompt, no picker). A result that needs UI = `RefreshRejectedException` = "Reconnect", which re-opens the picker for the same account. Token assumed good for 55 min (Google: 1 h); a 401 refreshes earlier.
3. **Library model.** One `cloud_folders` row per account (`item_id = "picked"`, "Picked songs") so the scanner, generation sweep, folder lock and workers are reused. Picked-but-unscanned ids live in private prefs (`cloud_gdrive_picks`); once scanned the `cloud_items` row is the record (a restored backup keeps its songs). The scan walks ids in sorted order with `files.get?fields=id,name,mimeType,size,md5Checksum,headRevisionId,modifiedTime,parents,trashed`, 25 per page, cursor `new:<lastId>` / `full:<lastId>` / `done`. A run right after a pick reads only the new ids; any other run (periodic twice a day, Rescan now) is a full re-check: trashed / 404 / 403 `appNotAuthorizedToFile` → removed (downloaded copies kept as local, the usual rule); a new md5 → tags read again; 403 rate limits (`userRateLimitExceeded`…) or 429/5xx stop the pass and remove nothing. Version (`?v=`, cache key) = md5Checksum, else headRevisionId, else modifiedTime. Parent folders aren't granted, so names come from tags or the file name, and covers only from embedded art.
4. **Streaming and download.** No pre-signed link: `CloudLink` gained `headers`; Drive's link is `files/{id}?alt=media` + `Authorization: Bearer` (its `toString` hides url and header values). Header-carrying links play through an OkHttp `HttpDataSource` with no interceptors (OkHttp drops `Authorization` on a cross-host redirect); the token is never in a URI, cache key or log. Length from metadata size (Drive may omit Content-Length). No `acknowledgeAbuse`: a 403 `cannotDownloadAbusiveFile` becomes "Google blocked this file" in the player and downloads.
5. **Quota.** Drive allows about 1 TB of downloads a day per Cloud project, shared by every user. Nothing enforces it now; revisit if the user count grows.
6. **Cloud setup** (project `stash-drive-512203`): Drive API + Google Picker API enabled; OAuth consent screen with the `drive.file` scope (non-sensitive, no verification needed); Android OAuth clients for `com.stash.app` (release SHA-1) and `com.stash.app.debug` (debug SHA-1). While the consent screen is in Testing, only listed test users can sign in and their grants expire after 7 days (the account then asks to reconnect).

## Save to Google Drive (owner decision 2026-10-20, app only)

1. **Triggers.** "Save to Google Drive" in the song, album and playlist menus (downloads only; an album or playlist sends its downloads and says how many weren't downloaded), and "Back up my downloads to Google Drive" on the Drive card: turning it on files today's downloads as EXISTING (offered once as "Back up N existing downloads"); every download made while it is on is queued. Network rule = the download setting (`wifiOnly`, as cloud scans use). Hidden when `GOOGLE_DRIVE_ENABLED` is false or no Drive account is connected.
2. **Scope.** Still `drive.file` only: it lets the app create files and see every file it created, on any phone signed in to the same account. Nothing is ever modified or deleted except a just-uploaded copy whose md5 doesn't match (deleted, try again). Removing a download or disconnecting never touches Drive.
3. **Where.** My Drive / Stash / <artist> / <album> / <title>.<ext>, the downloader's Artist/Album slugs (`LibraryLayoutResolver`, `singles` for no album). Folder ids are remembered per account and re-checked hourly; a trashed/deleted one is found again (by name, among Stash's own folders) or made again. Folders carry `appProperties.stashFolder=1`.
4. **Upload.** `cloud_uploads` (DB v62): one row per local track (PK = track id, CASCADE from the track and the Drive account). `CloudUploadWorker` (unique work `cloud_upload`, foreground `dataSync` notification) uploads QUEUED rows oldest first: Drive resumable sessions, 8 MiB pieces, 308 + Range → next offset, 5xx/429/403-rate-limit → back off through Drive's shared request gate and ask the session where it stands. The session address, size and md5 are saved on the row before the first byte, so a lost connection or process death resumes at the committed offset; a 404/410 session starts over. Drive full (`storageQuotaExceeded`) pauses backup ("Your Google Drive is full", "Try again"); signed out → the card's Reconnect, which resumes the queue; a vanished file → SKIPPED; 3 failed tries → FAILED.
5. **No duplicates.** Each file carries `appProperties.stashUpload=1` and `stashTrackKey` (sha-256 of the ISRC, else artist|title|seconds). Before uploading, `files.list q=appProperties has {key='stashTrackKey' …} and trashed=false`; a match with the same md5 is reused (reinstall, second phone).
6. **Linked.** After upload the Drive file becomes the existing track's `cloud_items` row in the account's second folder row, "Saved from Stash" (`item_id = stash-uploads`); the scan sees it as known and never adds a second song. A stream-only Drive song the scan filed first gives way to the local track, unless someone already used it (playlist, like, play): then nothing is linked and no data is lost. The track keeps playing its own file; its `cloud_uri`/source are untouched.
7. **Other phones.** The "Saved from Stash" row is scanned with one paged `files.list` for `stashUpload=1` (200 per page; a full listing every run, so the generation sweep removes trashed ones, after the same-account check). A listed file whose `stashTrackKey` matches a download on this phone with no cloud link (this phone's own saves after a disconnect/reconnect, or the same song downloaded on both phones) is linked to that download instead of added; no bytes are read for it. New Drive accounts get the row on connect; existing ones on the next scan.
8. **Gap.** If the user removes the local download, the track does NOT fall back to the Drive copy: the player falls back to the cloud copy only for `source = CLOUD` tracks (`PlayerRepositoryImpl` stream placeholder / file-failure fallback), and a linked track keeps its own source (a synced song streams its online match, as before). Making it play the Drive copy needs `cloud_uri` on non-cloud tracks plus those two player checks keyed on `cloud_uri`, and clearing it in `CloudDao.removeItems`; not done in this slice. If the track itself is deleted, its link goes with it and the next scan adds the Drive copy as a Drive song.

## Web player (after the app slice)

Built into the player, not a remote plugin (the plugin contract sends no credentials). Client-side PKCE, tokens and the index in IndexedDB, tags via `music-metadata` with a range tokenizer in a Web Worker, `<audio src=downloadUrl>` re-resolved before expiry, same `cloud:<provider>:<itemId>` refs. Reference implementation: Diffuse (icidasset/diffuse) for Dropbox/S3/WebDAV; Diffuse 3.x service worker for Drive's Bearer header.

## Not in this slice

WebDAV/SMB/S3/Subsonic, upload to cloud, web player. (Dropbox and OneDrive shipped on `feat/cloud-onedrive`; Google Drive as picked songs on `feat/cloud-gdrive`.)
