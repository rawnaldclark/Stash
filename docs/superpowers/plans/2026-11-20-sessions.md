# Sessions: build plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans. This file is the whole build in order; each step's task-by-task plan is its own file, written when that step starts (step 1's is `2026-11-20-sessions-step1-server.md`). Steps use checkbox (`- [ ]`) syntax.

**Goal:** Sessions, as the two specs describe: a host's live listening that anyone in Community can join, run like a DJ, in a room people want to hang out in.

**Specs (read both before any step):** `docs/superpowers/specs/2026-11-20-sessions-design.md` (the system) and `docs/superpowers/specs/2026-11-20-sessions-ux.md` (the room; wins where they differ). Mockups: the Design canvas https://claude.ai/artifact/8EFPDzJo4356LjrbCqnY7t (private to the owner).

**Architecture:** Two things on the server, both in the existing `stash-share` Worker (`infra/share-worker`):
- **Stations, votes, follows and the directory of live sessions:** D1 `stash-community`, migration `0007`, routes under `/v1/community/stations…`, `/live`, `/upcoming`.
- **A session room:** a Listen Together room made public (`src/room.js` stays pure and gains a `public` mode; `src/listen-room.js` gains the D1 writes for the directory).

On the phone, `ListenTogetherSession` runs public rooms the same way it runs private ones, with roles. The host's phone stays the player, and the room's queue is what it plays. Accepted requests, co-host adds and removals, and decks picks are therefore room-side queue edits that the host's phone already follows. Only **Skip** has to be forwarded to the host's phone. The screens live in `feature/community` (finding a room, your station) and `feature/nowplaying` (the room, the booth).

**Tech stack:** Cloudflare Workers (ES modules), Durable Objects, D1, `node --test` (Node 24, `node:sqlite` via `test/fake-d1.js`); Kotlin, Compose (Material3), Hilt, DataStore, OkHttp, kotlinx.serialization, JUnit4, MockK, Truth.

**The switch:** `SESSIONS` in `wrangler.toml` `[vars]`, `"0"` until the owner turns it on. While it's `"0"`:
- the Sessions routes answer 503 `sessions_off`;
- `POST /v1/rooms` refuses `public: true`;
- every app version hides Live now, Sessions and Go live.

So every step can merge and deploy on its own, and turning the feature on for everyone is one variable, once the owner says so.

## Rules for every step

- **Branches:** one worktree and branch per PR, cut from `origin/master` (`git fetch && git worktree add .worktrees/<name> -b feat/<name> origin/master`), with `local.properties` copied in. Survey `.worktrees/` and `gh pr list` before starting.
- **Commits:** stage explicit paths only, never `git add -A` or `git add .`; check `git diff --cached --name-only` before each commit. Commit small and push often (push WIP to `wip/<branch>`, so CI on the PR isn't cancelled). End every commit with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.
- **Tests:** test first. Server: `cd infra/share-worker && npm test`. App: the module's `testDebugUnitTest` with `--max-workers=3`. Master CI is green, so red means your change.
- **Phones:**
  - Pixel 5 rig: `adb -s 192.168.137.230:5555`. Never sleep or lock it (KEYCODE_WAKEUP only).
  - Owner's Pixel 6 Pro: debug app only, and only with the owner's OK. Gate every tap on `mCurrentFocus` in the same command.
  - Install with `assembleDebug` + `adb -s … install -r`, never `gradlew installDebug`. Check the gradle exit code, the APK's mtime and its versionName before any device proof.
  - The Room DB stays at **80**: nothing here adds a table on the phone (recaps and listening totals live in DataStore), so no step can put a lower DB version over a phone's data.
- **Deploys:** every Worker deploy and every D1 migration on `--remote` needs the owner's go, asked each time.
- **Plain words in the UI:** no machinery in strings ("room", "DO", "directory", "protocol" never reach a screen).

## Decisions this plan makes inside the specs

These came up while reading the code. Each one keeps what the specs promise and changes how it's built. Step 1 notes them in the system spec.

1. **Listeners don't hold up the music.** In a public room the ready handshake waits for the host only, never for 50 strangers. Listeners who aren't ready join mid-song, the way a late joiner does today. Without this, one slow phone would add up to 8 s of silence to every song for everyone.
2. **Status changes stay quiet.** A public room sends `members` when someone arrives or leaves, not when a listener's buffering status changes. That's up to 54 sockets, and statuses only matter for the handshake.
3. **Who you are in a room comes from your Community key, never from a claimed id.**
   - The app sends its key in `hello`, and the room's shell hashes it, as it does the host key.
   - The pure room sees only the hash. Clients never see anyone's hash: they boot and make co-hosts by `memberId`.
   - This replaces the system spec's client-sent `listenerId`, which anyone could forge. It also replaces `cohostKey`: co-host status is kept by key hash, so a co-host who reconnects is still a co-host.
4. **Co-hosts edit the room's queue directly.** Accepting requests, adding and removing songs use the room-side queue edits that guest adds already built (`insertAdds`, `unqueue`); the host's phone follows the queue it gets. Only **Skip** goes to the host's phone, as `{t:"command", action:"skip"}`. Reordering stays with the host in v1. If the host's phone isn't connected, a co-host's Skip is refused at once with "The host is reconnecting" instead of waiting 10 s.
5. **Old apps can't walk into a public room.** Public rooms refuse a `hello` below protocol `v: 3` with close code `4426 update`. An older app has no Live now, but a room code can still be typed.
6. **The live directory can't be overwritten by a dead room.**
   - The `live` row is keyed by station, and each room updates only rows that carry its own code. A host who restarts gets a new room whose row replaces the old one, and the old room's late writes change nothing.
   - Every write also checks the station; if it was removed, hidden or blocked, the room ends with `station_removed`. That's how the owner's command-line `remove` reaches a live session within a minute.
7. **Live cards show initials, not names.** Names are for the people in the room. A Live card is seen by everyone, so `live.crowd` holds up to 4 `{i, id}` pairs: an initial, and the per-session member id that picks the face colour, which links to nothing else.
8. **Animated reactions are drawn in Compose**, not shipped as 12 WebP files: no art assets to make, crisp at any size, and each one only a few KB in the APK. The ids and the room's checks stay as the system spec's §5 says.
9. **The feed is built on each phone** from what the room already sends (arrivals, phrases, picks, favourites). The room relays phrases and keeps per-song counts; there's no `feed` message.
10. **The scoreboard is in.** Owner, 2026-11-20: "yes counting is fine". Step 5 counts daily totals only, with no person in them: sessions, listener-minutes, median minutes a listener stays, the share of listeners who react / say / save / request, requests played, follows per session, and returning listeners per station per week.
11. **Upcoming isn't cached through the Cache API.** On the stashfm.app zone the Cache API ignores the query string (memory: `infra_cache_api_ignores_query_on_stashfm_zone`), so `upcoming?limit=` would mix up answers. It's worked out per request; it's cheap at this size.

## The steps

Each step is a PR (step 1 is two), tested on phones before the next starts. Server work that a later step needs ships with that step, deployed before its app PR merges. Older apps never send the new messages, so they're unaffected.

### Step 1: the server (two PRs) — `2026-11-20-sessions-step1-server.md`

**1a, stations** (`feat/sessions-stations`):
- Migration `0007_sessions.sql`: `stations` (+ `vibe`), `station_votes`, `station_heard`, `station_follows`, `live`.
- Routes:
  - stations: create, mine, read, update, delete;
  - vote and heard (the post rules: capped per network, the heard gate behind `HEARD_REQUIRED`, hidden at −3 unless vouched);
  - follow, and the list of stations you follow;
  - `live` (ranked: net votes + listeners);
  - `upcoming` (time zones and DST, next 24 h).
- Cleanup in the daily cron: stale `live` rows, and stations not live for 7 days, with their votes, heard marks and follows.
- `npm run community -- station list|remove|restore|block`.
- The `SESSIONS` switch, and the station page `GET /s/{id}` with its `stashfm.app/s/*` route.

**1b, public rooms** (`feat/sessions-rooms`):
- `room.js` public mode: roles, the 54 cap, protocol v3 only, the host-only handshake and the quiet members list.
- Endings: host gone 60 s, paused 15 minutes, 12 hours.
- Booting, by key hash.
- Requests, held to the host and co-hosts, with Auto-accept; the 3-per-listener and 30-in-all caps.
- Co-hosts, up to 3: room-side adds and removals, Skip forwarded.
- Presence (in the booth or away), and the `session` message.
- `listen-room.js`: the directory writes (first song, each song, pause and play, once a minute, the end) with the station check.
- `POST /v1/rooms {public, stationId}` with the key, ownership, hidden and blocked checks.

Deploy 1a + 1b with `SESSIONS = "0"`, after the owner's go. Smoke test afterwards: a private Listen Together room on two phones works exactly as before.

### Step 2: listen, go live, the room, Live now, follow (app) — `feat/sessions-listen`

- **Models and client.**
  - `core/model/community/Stations.kt` holds the station, live, follow and upcoming models.
  - `RoomProtocol` v3: hello `communityKey`, `session`, the `ended` reasons, `requestPassed`, `command`, and the messages step 3 uses, so the protocol lands once.
  - `core/data/community/StationsApiClient` + `StationsRepository` are refused while Community is off, like `CommunityRepository`.
  - `RoomApiClient.create(public, stationId, key)`.
  - Station listening time goes to DataStore, which sends `heard` once 2 minutes are reached across sessions.
- **The engine.** `ListenTogetherSession`:
  - `Command.TuneIn(code)` and `Command.GoLive(stationId)`;
  - public-room roles in `ListenTogetherState.InRoom` (`station`, `role`, `listeners`, `cohosts`, `presence`);
  - the new `ended` reasons with their messages: "Maya's session ended", "You were removed from this session";
  - your own queue kept and offered back when you leave.
- **Finding a room** (`feature/community`):
  - Community's Home section opens with **Your stations** (round cards, live first) and **Live now** (wide cards: art, LIVE · count, name, vibe line, crowd initials, Following, score). Mockup: Home.
  - **Sessions** screen with the Live tab: stations you follow, then everyone live, ranked. Mockup: Sessions. Upcoming stays hidden until step 6.
  - **Your station:** name, vibe line, link and Share, followers, regulars (the count arrives in step 5), Go live now, the 7-day note, Delete. The auto-live controls stay hidden until step 6.
  - **Go live** sheet the first time: name, "What's playing tonight?", the one-sentence share notice. After that, one tap from Now Playing or Your station.
- **The room** (`feature/nowplaying/session/`):
  - The room screen replaces Now Playing while you're in a session. From the top:
    - header: collapse, name, LIVE · count, Follow, the menu (Leave, Share station, About);
    - the vibe line, the art, title and artist;
    - the crowd band: the booth (host with crown, co-hosts), the floor (faces, +N, and a sheet of everyone's names);
    - reactions, with today's six emoji rising from faces;
    - Up next (one line);
    - the bar: Request (disabled until step 3) and React.
  - The vote pill, greyed out with "Listen 2 minutes to vote" until then.
  - Leaving after 2 minutes or more shows the leave sheet, once per session: rate (▲ ▼) and Follow.
  - The mini player and Now Playing show **LIVE** whenever you're on the air (host) or in a session (listener).
  - The booth (host): player controls, crowd list, End now.
- **Links:** `stashfm.app/s/{id}` opens the station (manifest `pathPrefix="/s/"` for both hosts; the app routes it to the room when live, else to the station).
- **First tune-in:** one line saying everyone in that session will see your name. Joining makes a Community key if the phone has none (`CommunityKeyStore.key()`).
- **Tests:**
  - repository: off-switch, errors, heard at 2 min;
  - session engine: tune in, go live, the ended reasons, no hand-over in public rooms, old queue restored;
  - ViewModels: Live now ranking as the server sends it, Follow optimistic with roll-back, the vote gate.
- **Phones:** Pixel 5 hosts, Pixel 6 tunes in from Live now. Check sync, reactions both ways, Follow, the vote after 2 min, host network cut (ends at 60 s), pause 15 min (ends), and the station link from a chat app.

### Step 3: the DJ: requests, co-hosts, booting, presence (app) — `feat/sessions-dj`

- **Request** (mockup: Request a song):
  - search inside the room, with a Request button on each result;
  - **Your requests** with their states (Up next, Waiting, take back) and "Maya passed on Nights. Only you see this.";
  - the 3-waiting cap.
  - While you're in a session, song menus anywhere in the app show **Request** instead of Play next and Add to queue.
- **The booth** (mockup: The booth):
  - requests waiting, each with Next / Queue / Pass;
  - Auto-accept;
  - tap a face for Co-host or Boot, plus "5th time here" (step 5 fills that in);
  - the crowd-energy line: reactions in the last minute, counted on the phone.
- **Co-hosts:** their room gains the requests list, add (room-side), remove (room-side) and Skip. "The host is reconnecting" when it's refused.
- **Presence:**
  - the host app sends `presence` (`booth` while Stash is on screen, `away` otherwise);
  - listeners see "Maya is in the booth" or "Maya is away · requests wait" / "· requests play automatically";
  - away with requests waiting: one quiet notification ("2 requests waiting"), not one per request.
- **Tests:** request flow against a fake room (accept, pass, auto-accept, the cap); a co-host's Skip; boot (the listener's screen and its rejoin refused); presence from the app being in the foreground.
- **Phones:** Pixel 5 hosts, Pixel 6 requests and then co-hosts; a third member from an emulator on the PC (or the web player once it can listen, not in v1).

### Step 4: phrases, the feed, saves, crowd favourites, animated reactions — `feat/sessions-room-life`

- **Server (deployed first):**
  - `say {phrase}`: the 10 ids, one per 3 s per person, repeats folded by the room within 10 s ("×4");
  - `react {anim}`: the 12 ids;
  - `saved {trackKey}`: counted once per person per song;
  - `songStats {trackKey, reactions, saves, favourite}`: sent on change, at most once every 2 s, with the favourite rule (a third of the room and at least 3 people, while the song plays);
  - tests for each.
- **App:**
  - the **React tray**: the six emoji, the 12 moves drawn in Compose, the 10 phrases, translated; "Who is this?" also opens the song for you;
  - the **feed** under the crowd: the last 4 lines fading, built from events, kept only for the session;
  - the **heart**: saves to Liked Songs through the existing like action (Download mode rules as everywhere), with "9 saved this";
  - the **Crowd favourite** badge and its feed line;
  - for a newcomer, "Hi all" lit for 10 s.
- **Phones:** phrases and moves both ways, a favourite reached with three phones (emulator as third), saves landing in Liked Songs.

### Step 5: last song, the recap, regulars — `feat/sessions-recap`

- **Server (deployed first):**
  - `lastSong` from the host: everyone gets `lastSong`, and the room ends after that song with `ended {reason: "last_song"}`;
  - `station_regulars (station_id, listener, sessions, last_at)`, migration `0008`: the room counts a session for a listener who stayed 10 minutes or more in total, when they leave or the room ends;
  - the shell reads a listener's count on `hello` and passes it into the pure room, so members carry `regular` (3 or more), and the host alone gets `visits`;
  - rows not visited for 60 days are swept by the cron.
  - the scoreboard (decision 10): a `session_stats` table of daily totals, migration `0008` too, written by each room when it ends; returning listeners come from `station_regulars`; `npm run community -- stats [days]` prints them.
- **App:**
  - **End** offers End now / End after this song, and everyone sees the "Last song" banner;
  - the **listener recap** (mockup: Recap): time listened, songs played, people who came by, your picks that played and their reactions, crowd favourites, songs you saved, when the host is on next, rate and Follow;
  - the **host recap** (mockup: Host recap): time on air, people, peak, new followers (the follower count before and after), requests played, favourites, most saved, regulars and new regulars;
  - recaps are built on the phone from the session's messages and kept 7 days in DataStore (at most 20), and the Sessions screen has a "Recent" entry to reopen them;
  - the regular star and "Ben is back" in the feed.
- **Phones:** a 10-minute session that makes someone a regular after three runs (shortened by a debug-only override of the 10 minutes); recaps on both phones; End after this song.

### Step 6: auto-live and Upcoming (app) — `feat/sessions-autolive`

- **Your station:** Off / On a schedule / Always, the hours editor (up to 7 windows, day + start + end, the phone's time zone sent with them), and Auto-accept.
- **`SessionAutoLive`** (`core/media`) goes live when playback starts inside a window, when a window opens while you're playing, and on any playback for Always. At a window's end it ends after the current song. It never goes live:
  - in Download mode;
  - while in a private Listen Together room;
  - while Community is off;
  - while the station is hidden or blocked;
  - without a network (it waits, silently).
  The LIVE pill always shows, and the first auto-live of a day posts a quiet notification with End.
- **The Upcoming tab**, and the next hours of the stations you follow in Your stations.
- **Tests:** the rules table (windows across midnight, DST weeks, the Always mode, each "never"), the end-of-window song finish, the notification once a day.
- **Phones:** a schedule window 2 minutes from now on the Pixel 5; Download mode on, no going live.

### Step 7: open decks — `feat/sessions-decks`

- **Server (deployed first):**
  - decks in the public room: `decks {open}` (host), `deckJoin {track}`, `deckPick {track}`, `deckLeave`, `deckRemove {memberId}` (host), and `decksState` to everyone;
  - up to 5 on the decks (the host plus 4), then a line;
  - turns go one song each in order. At each song change, the room puts the next DJ's ready pick at the front of the queue as an add, which the host's phone plays from the queue as it does today. The host's turn is the host's own queue.
  - no pick ready on your turn: skipped; skipped twice in a row: off the decks, with a feed line;
  - closing the decks drops every ready pick.
  - Tests cover each rule.
- **App:**
  - **Join the decks** in place of Request while the decks are open;
  - the decks card (who's on, NOW and NEXT, open spots, the line);
  - **Your pick** with Change, "You're up next";
  - Leave the decks;
  - the booth's **Open the decks** switch and taking someone off.
- **Phones:** host plus two DJs (emulator as the third), a full turn round, a DJ with no pick skipped twice.

## Turning it on (after step 3 at the earliest; the owner decides)

1. The owner tries a session on their own Pixel 6 Pro (release app), host and listener.
2. Release notes are written, plain language and headline first, and the owner approves them before any tag.
3. With the owner's go: `SESSIONS = "1"`, deploy, then check that `GET /v1/community/live` answers 200.

Rollback is `SESSIONS = "0"` and a deploy. Live sessions end within a minute, because their directory writes are refused.

## Risks to watch

- **Fan-out:** 54 sockets in one Durable Object. Step 1b adds a `node` load script, `scripts/room-load.mjs`, that connects 54 sockets to `wrangler dev`, plays 20 songs and sends a reaction every second from each. It reports the CPU time per message and the largest stored state.
- **Auto-live surprising someone:** the LIVE pill always shows, the first auto-live of the day posts a notification, and Download mode never goes live.
- **A station name as a slur:** votes hide it at −3, and the owner's `station remove` ends it within a minute (decision 6).
- **D1 write volume:** about one `live` write per minute per session plus one per song. That's well inside the Workers Paid limits (memory: `reference_cloudflare_workers_paid_plan`).
